# 实施计划

## 顺序

1. **组件与分区**：固定引入 FlashDB 2.2.0 TSDB/FAL 源码，建立 `esp_bms_flashdb` 组件、ESP-IDF 端口、4 KiB 分区检查和板级逻辑槽容量；更新两个分区表并删除 Web 资源嵌入/根路由。
2. **记录编码**：实现 32 字节联合样本、故障事件、会话锚点、版本/有效性位、静态断言和无效字段规则；补充 session sequence 的 NVS 一次写入。
3. **存储生命周期**：实现初始化恢复、三槽选择、最旧槽清理、经典 ESP32 截断、写满状态、故障独立 TSDB、FlashDB 错误降级和日志。
4. **采样接入**：在现有运行时调度中每秒形成一次 GPS+BMS 联合快照；接入 GPS UTC 锚点和保护/警告状态变化；成功写入后停用旧 GPS 轨迹 blob 的周期性 NVS 写放大并完成一次性迁移。
5. **查询契约**：增加会话、联合样本、故障分页 API，保留 `/api/gps/track` 兼容投影和存储状态字段；移除热点 Web 页面但保留 Android 所需的网络路由。
6. **Android**：扩展 `DeviceApi` 的类型化响应和游标，增加会话列表、GPS 轨迹、BMS 曲线、故障日志及未校准/截断/降级状态；不把响应字段散落解析在 Activity 中。

## 验证

- 主机自检：记录编码/解码、相对时间到 UTC 锚点换算、严格递增键、三槽保留、最旧槽清理、故障状态去重、截断状态和坏记录跳过。
- 固件构建：两个现有板型分别执行配置生成、`./scripts/esp-idf-env.sh build`，检查分区边界、镜像大小和 Web 资源不再嵌入。
- Android：`RUN_TESTS=1 ./scripts/build-android-cast.sh`，覆盖 API JSON 缺省字段、游标分页、空会话、未校准和容量状态。
- 真机：持续 GPS+BMS 写入 1 秒采样，重启恢复，GPS 延迟锚定，历史分页，故障变化，S3 三槽滚动，经典 ESP32 截断和 FlashDB 损坏恢复。
- 完成固件改动后按硬件规范通过 RFC2217 做一次构建/刷写尝试，并记录结果。

## 风险与回滚点

- FlashDB 源码/端口不兼容 ESP-IDF 6.0.2：先用最小 TSDB/FAL 自检和双板构建验证，失败时回滚组件接入，不改 NVS 设置路径。
- 分区不足或编码尺寸超预算：构建阶段拒绝错误分区，保留经典板截断策略，不侵占 OTA/NVS。
- 采样层改动影响运行时锁：存储追加只在快照副本上执行，禁止持有 GPS/BMS 锁做 Flash 擦写；异常时实时界面优先。
- API 兼容风险：保留 `/api/gps/track`，新历史接口版本化；Android 先容错缺省字段再启用图表。
