# FlashDB 时序存储

## Goal

使用 FlashDB 为设备提供掉电可恢复、可按时间查询、容量有界并自动滚动的本地历史存储，将同一时刻的 GPS 坐标与 BMS 遥测保存为联合行驶样本，并独立保存 BMS 故障事件；继续使用 ESP-IDF NVS 保存设置、绑定信息、Wi-Fi/NimBLE 数据及其他小型固定状态。

## Confirmed Facts

- 用户已明确选择 FlashDB，并要求 GPS 轨迹、BMS 采样和故障日志全部纳入本任务。
- 用户要求 BMS 遥测与 GPS 坐标每 1 秒使用相同采样时刻并保存在同一条行驶样本中；典型单次记录时长为 30 分钟至 5 小时。
- 每次设备启动后的首个有效样本开启一份新记录，最多保留 3 份记录。
- 新记录开始前必须按一份最长 5 小时记录的预算检查空间；不足时从最旧记录开始删除，直到空间满足要求且记录数低于 3。
- 两个现有开发板实体均有 TF 卡座，但仓库尚未配置接口类型和 GPIO；用户决定本任务暂不启用这两个板型的 TF 功能，仅保留后续接入边界。
- 当 TF 不可用且板载 Flash 无法容纳完整 5 小时记录时，用户选择保留一份按实际容量截断的记录，而不是禁用历史持久化。
- 用户确认取消设备热点 Web 页面；设备继续提供 SoftAP 和 HTTP API，由 Android APK 承担设置、OTA、历史会话、GPS 轨迹、BMS 曲线及故障日志界面。
- 当前内嵌 `main/web/index.html` 约 51 KiB，删除后主要减少固件 Flash 占用；APK 仍依赖 HTTP API，因此 Wi-Fi、SoftAP、HTTP server 及其运行时 RAM 不能移除。
- 当前 GPS 每 5 秒最多接受一个有效定位点，并将固定 128 点、1544 字节的完整轨迹 blob 写入 16 KiB NVS；连续有效定位时存在明显写放大。
- 当前 GPS RMC 解析已经提供有效 UTC 日期和时间，但轨迹记录仍使用设备本次启动后的秒数，不能直接满足跨重启的严格递增时间戳要求。
- 当前固件没有启用 SNTP、外部 RTC 或 Android 校时接口；GPS 是唯一可靠绝对时间源。现有 GPS 运行时投影只保存 UTC+8 的年月日时分，尚未向存储层提供完整 UTC 秒。
- 用户接受：UTC 尚未可用时先按单调相对秒记录；首次 GPS UTC 到达后写入会话时间锚点并换算查询时间；整段未校准的会话仍可按相对时长查看，但不参与 UTC 范围查询。
- 当前 BMS 快照已经包含包电压、电流、SOC、容量、单体电压统计、温度、保护码和警告码；不同协议只记录经过有效性检查后实际提供的字段。
- 当前保护与警告状态保留未知位，并以独立的 protection/warning 概念投影到运行时快照。
- 当前容量估算历史和骑行峰值记录都是有界小型数据。它们继续留在 NVS，不在本任务中改造成逐点时序数据。
- 当前 ESP32-S3 16 MiB 分区表包含约 3.94 MiB 的未挂载 `storage` 区域；经典 ESP32 4 MiB 分区表在 OTA 分区后保留约 192 KiB 未声明空间。
- 当前两个固件板型目录都没有 TF/SD 接口、引脚或模块开关；实体卡座信息尚未进入代码权威。仓库中的自研 ESP32-S3 R1 硬件是另一套设计，其“不加 TF”的决策不能用于否定这两个开发板上的实体卡座。
- FlashDB 上游 ESP32 示例使用独占自定义分区和 `esp_partition_*` 端口；示例注明基于 ESP-IDF 4.4.1，本项目目标 ESP-IDF 版本需要独立验证。

## Requirements

- R1. 以项目组件方式集成固定版本的 FlashDB，只启用本任务实际需要的 TSDB 能力，不引入 FlashDB KVDB 替换 NVS。
- R2. FlashDB 在板载 Flash 上使用独占物理分区；联合行驶样本与故障事件使用彼此隔离、各自滚动的有界存储区域，高频行驶样本不得淘汰故障事件。
- R3. 设置、语言、亮度、BMS/控制器绑定、Setup AP、Wi-Fi、NimBLE、触摸校准、容量估算和骑行峰值记录继续使用现有 NVS 路径。
- R4. 行驶样本以 1 秒为固定采样周期，使用统一 UTC 时间戳，将同一采样时刻的 GPS 坐标和 BMS 遥测写入同一固定大小记录，并能跨重启保持时间顺序。
- R5. 联合记录使用字段有效性标志；GPS 或 BMS 短暂无效时不得伪造数据，也不得因一侧无效而丢弃另一侧仍有效的数据。
- R6. 联合记录使用紧凑定点编码，目标 payload 为 32 字节。数据覆盖纬度、经度、包电压、带符号电流、SOC、单体最高/最低/平均/压差、最多 6 路温度、BMS 类型和有效性/状态标志，不保存原始 BLE 帧。
- R7. 故障日志按保护位或警告位的状态变化追加事件，保留 BMS 类型、绑定设备身份、已知代码及未知位；稳定不变的故障状态不得周期性重复写入。
- R8. 联合行驶样本和故障事件均支持按 UTC 时间范围查询，结果按时间排序，并通过有界 `limit` 和游标或等价机制避免一次性占用大块 RAM。查询接口应允许客户端从联合样本投影 GPS 轨迹或 BMS 曲线。
- R9. 提供版本化的 Android 设备 HTTP 契约并迁移现有 Android 客户端；移除热点 Web 根页面不得影响 `/api/*`、OTA 或投屏接口。
- R10. 经典 ESP32 与 ESP32-S3 使用板级分区配置定义可用容量；滚动发生时不得影响 OTA、NVS 或其他数据分区。
- R11. 初始化、追加、查询、滚动和故障恢复必须有明确错误处理；FlashDB 不可用时设备的 BMS 实时显示、GPS、BLE、Wi-Fi 和 OTA 仍能运行，并报告持久化降级状态。
- R12. 旧版有效 GPS NVS 轨迹应支持一次性迁移。只有 FlashDB 写入成功后才能清理旧 key，重复启动不得重复导入。
- R13. 数据格式必须带版本，并允许后续固件识别旧记录；不兼容记录不得导致启动失败或静默解释成错误数据。
- R14. 分区和代码必须遵循现有固件裁剪体系：未启用 GPS 或 BMS 的构建不得写入对应字段或数据库。
- R15. 每次设备启动后的首个有效联合样本开启一份记录；单份记录按最长 5 小时、18000 条样本管理，记录结束条件为关机/重启或达到容量上限。
- R16. 启动新记录前，存储层必须同时检查完整一份最大记录的可用空间预算和现存记录数。若可回收，则反复删除最旧的完整记录，直到可用空间不低于预算且旧记录少于 3 份；任何时刻最多保留 3 份记录。
- R17. 两个现有板型本次只启用板载 Flash 后端，并根据实际分区大小判断是否能容纳完整记录及故障日志保留区，不得仅按芯片标称 Flash 容量推断。
- R18. 存储模块不得把板载 Flash 地址或 ESP-IDF 分区访问散落到采样、查询和 HTTP 层；后续取得 TF 接口与 GPIO 后，可在存储边界内增加 TF 后端，但本任务不增加未验证的 TF 挂载代码、引脚占位或运行时探测。
- R19. 若板载 Flash 在预留独立故障日志空间后仍无法提供约 896 KiB，则联合样本区使用实际可用容量保存一份截断记录；写满后结束该记录并明确报告容量截止，不在同一次启动中覆盖其开头或自动开启下一份记录。
- R20. 固件不再嵌入或提供 `main/web/index.html`，访问 `/` 返回稳定的无页面响应；SoftAP、设备发现/连接方式和现有 HTTP API 服务继续保留。
- R21. Android APK 提供最多 3 份历史会话的列表和存储状态，并可查看选定会话的 GPS 轨迹、BMS 时序数据和故障事件；分页加载不得一次将 5 小时完整数据复制到 ESP32 RAM。

## Capacity Estimate

- 规划按 FlashDB 2.2.0、4 KiB 擦除扇区、64 位时间戳和 32 字节固定 payload 估算。固定记录索引约 16 字节，每条联合样本约占 48 字节；计入扇区头和尾部余量后，每个 4 KiB 扇区约保存 84 条。
- 1 秒采样时：30 分钟为 1800 条，1 小时为 3600 条，5 小时为 18000 条。按每扇区约 84 条估算，5 小时需要约 215 个 4 KiB 扇区，即约 860 KiB；为扇区边界和元数据预留后，每份记录按约 896 KiB 检查。
- 最多 3 份完整记录约需 2.625 MiB，另需独立故障日志保留区。ESP32-S3 当前约 3.94 MiB 的可用 `storage` 分区具备规划空间；经典 ESP32 当前约 192 KiB 的尾部空间无法容纳一份完整的 5 小时记录。
- 空间检查使用运行时后端报告的实际可用容量。删除最旧记录只能回收完整会话，不能删除 NVS、OTA、故障日志或其他分区数据。
- 小容量 Flash 的截断记录不再强制满足约 896 KiB 启动门槛，其最大条数由联合样本分区可用扇区数计算并在状态接口中报告；当前经典 ESP32 的约 192 KiB 尾部空间还需扣除故障日志区和元数据，实际留存显著少于 5 小时。
- 以上是源码级预算，不代替实际编译后的结构体断言、分区检查和真机滚动验证。

## Acceptance Criteria

- [ ] 经典 ESP32 与 ESP32-S3 的目标固件均能构建，分区表不与 bootloader、OTA、NVS 或其他已声明分区重叠。
- [ ] FlashDB 初始化后，联合行驶样本与故障事件分别追加并独立滚动；填满行驶样本不会删除故障事件。
- [ ] 连续有效定位不再每 5 秒把完整 GPS 轨迹 blob 写回 NVS。
- [ ] 连续有效运行时每秒至多追加一条联合样本，5 小时边界为 18000 条；GPS 或 BMS 单侧更新频率较低不造成额外重复记录。
- [ ] GPS 记录使用可跨重启排序的 UTC 时间，重启后新记录不会因时间回退被 FlashDB 丢弃。
- [ ] 每条联合样本中的 GPS 与 BMS 字段来自同一采样时刻；任一侧无效、部分、断开或超时时以有效性标志表达，不产生伪造值，也不丢弃另一侧有效数据。
- [ ] 保护/警告集合发生新增、清除或变化时各产生一条事件，未知位可查询，状态不变时不重复写入。
- [ ] 联合样本和故障事件均可按时间范围分页查询；客户端可从联合样本得到 GPS 轨迹或 BMS 曲线，空结果、超范围和已滚动数据返回明确且稳定的响应。
- [ ] 现有 NVS 设置、绑定、Setup AP、Wi-Fi/NimBLE、触摸校准、容量估算及骑行峰值在升级后保持可用。
- [ ] 旧 GPS NVS 轨迹只迁移一次；模拟迁移中断后不会丢失唯一副本或重复导入。
- [ ] 模拟写入中断、损坏记录和分区写满后，数据库可恢复或受控降级，主设备功能仍可启动。
- [ ] 开始新记录前，若可用空间小于约 896 KiB 或已有 3 份记录，系统按时间从旧到新删除完整记录，直到满足启动条件；删除不会越过联合样本存储边界。
- [ ] 两个现有板型均不初始化或探测 TF 卡，构建产物只使用板载 Flash；存储状态明确报告 `flash` 后端和完整/截断容量。
- [ ] 最多保留 3 份完整记录，跨重启仍能识别记录边界、顺序和最旧记录。
- [ ] TF 不可用且板载 Flash 小于完整记录预算时，系统仍可启动一份截断记录，并提前报告可保存的估算时长；写满后保留该记录的开头和明确的容量截止状态，不循环覆盖为一段来源不明的尾部数据。
- [ ] 固件镜像不再包含约 51 KiB 的热点 Web 页面，浏览器访问根路径不会返回旧管理界面；Android 仍能通过 SoftAP 调用设置、OTA、状态、投屏及新增历史 API。
- [ ] Android 可列出会话和存储后端/容量状态，选择会话后分页查看 GPS 轨迹、BMS 曲线及故障日志，并正确显示截断、已满、TF 拔出和存储降级状态。
- [ ] 有可执行自检覆盖联合追加、时间范围查询、两库独立滚动、跨重启时间、故障去重、旧数据迁移和掉电恢复关键路径。
- [ ] 真机验证覆盖至少一次持续 GPS+BMS 写入、重启恢复、历史查询和滚动边界，并记录 Flash/RAM 开销。

## Out Of Scope

- 使用 FlashDB KVDB 替换 NVS。
- 保存原始 BLE 通知帧或未经解析的完整 BMS 协议数据。
- 云端同步、账号体系或远程数据库。
- TF 卡挂载、文件系统、插拔检测、TF 与板载 Flash 双写或运行时后端切换；待板级接口和 GPIO 配置完成后另行实现。
- 热点 Web 页面及任何浏览器端设置、OTA 或历史查看界面。
- 重写 BMS 协议解析、容量估算算法或既有骑行峰值算法。
- 删除现有热点 Web 或 Android 客户端接口。
