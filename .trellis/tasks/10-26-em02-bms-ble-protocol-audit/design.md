# 设计：EM02 与 BLE 协议一致性

## 架构边界

- EM02 遵循现有保护板分层：纯协议模块负责 Modbus 请求、流组帧、CRC、身份和遥测解码；`esp_bms_bms_ble` 负责 GATT、轮询状态和快照投影；runtime 负责枚举、持久化与配置接口；Web/LVGL 只管理可见配置入口。
- BMS 新枚举值追加为 7，保留 0–6 的 NVS/API 含义。EM02 GATT UUID 通过同一 BMS BLE 连接发现逻辑绑定，FFE2 使用 acknowledged write，FFE1 订阅通知。
- EM02 协议严格只读。设备身份帧未通过 `EM02`/`LX-EM02` 字符串校验时，不进入已识别状态，不将其数据投影为保护板遥测。
- 复用 `esp_bms_bms_protocol.h` 现有遥测字段；不增加未被产品展示或安全决策消费的协议字段。按 EM02 已确认的数据映射现有包电压、电流、SOC、容量、单体、温度字段。
- 蓝宝配对码沿既有 pending HTTP config → runtime 主循环 → NVS 保存路径传递。GET 配置仅返回 `bluebabe_code_saved`，绝不回显码值；POST 只在提交非空六位数字时更新，留空保持原值。
- LVGL 保留蓝宝型号行用于显示 Web 当前配置，但该行以禁用状态渲染，去除可点击标记并在 action 回调处再次拒绝 Bluebabe action；Web 是唯一可切换入口。
- 控制器通知接收容量与协议最大帧长统一支持甲胄最大 envelope（4 字节头 + 192 字节载荷），使用有界复制；过大输入安全拒绝并计入诊断日志。

## 协议审计方法

1. 按 `motexa-baseline.md` 设备清单逐个检查 7 种保护板和 16 种控制器：GATT 服务/特征 UUID 与属性、请求字节、响应 framing、长度上限、CRC/校验、拆包/粘包、字段偏移/单位和状态推进。
2. 将每项结论标为“参考一致”“确定性错误”“仅功能缺失”或“需真机确认”；Daly 等无 Motexa 参照的协议仅做标准/内部自洽检查，不伪称交叉验证。
3. 对确定性错误先补固定字节/构造帧回归测试，再做最小修复；不根据语义猜测修改协议。
4. 更新 `docs/protocols/cross-verification.md` 和 `motexa-baseline.md`，将 host、固件构建、真机 HCI 证据分别列清。

## 兼容性与安全

- 不改现有枚举值、默认 BMS 类型或旧配置解释。
- 配对码已存在 NVS 格式继续使用；不迁移已保存的蓝宝码。配置 JSON 停止泄漏明文值；页面只展示“已保存”状态，输入保持空白。
- EM02 多寄存器响应的 byte-count 是 178/108/90/96，对应完整帧长 183/113/95/101；不能把 byte-count 误当帧长。
- 参考 APK 自述 EM02 实体设备待验证；无法真机验证时，在报告和风险说明中保留此限制。

## 回滚

按模块回滚 EM02 注册/枚举/页面入口、蓝宝配置/UI 限制或控制器缓冲调整即可；NVS 中现有类型值与配对码格式保持兼容，无需数据迁移。
