# JBD BMS BLE Protocol

## Scenario: Read-Only JBD Frame Assembly

### 1. Scope / Trigger

- Apply when changing JBD BLE polling, notification assembly, or telemetry decoding.
- The firmware remains read-only: authentication credentials and register writes require a separate design.

### 2. Signatures

- Parser: `esp_bms_jbd_feed(stream, stream_len, stream_capacity, chunk, chunk_len, telemetry)`.
- Regular response: `DD command status length payload checksum:u16 77`.
- Authentication response: `FF AA command length payload checksum:u8`.
- Upstream compatibility baseline: `syssi/esphome-jbd-bms` commit `99cf7c15dbc2056295c88abc3fae7c1d83e6fb7f`.

### 3. Contracts

- Regular frames use a 16-bit big-endian two's-complement checksum over `status`, `length`, and payload.
- Authentication frames use an 8-bit additive checksum over `command`, `length`, and payload; consume valid frames without changing authentication state.
- Reject non-zero regular-frame status before decoding telemetry.
- Treat 41 bytes as the largest supported JBD response. A larger declared frame must resynchronize immediately instead of waiting inside the 320-byte runtime stream buffer.
- Decode command `0x03`; consume valid `0x04`, `0x05`, and `0xAA` responses without publishing false telemetry.
- After returning the first decoded `0x03` frame, preserve trailing bytes for the next call.

### 4. Validation & Error Matrix

| Input | Required behavior |
| --- | --- |
| Fragmented valid frame | Buffer until complete, then decode once |
| Valid authentication frame | Consume without telemetry or state transition |
| Bad checksum, terminator, or non-zero status | Drop at least one byte and resynchronize |
| Declared frame longer than 41 bytes | Reject immediately and scan for the next frame |
| Chunk larger than stream capacity | Reject and clear buffered data without copying |
| Multiple frames in one notification | Consume in order and preserve bytes after the first telemetry result |

### 5. Good / Base / Bad Cases

- Good: a fragmented authentication frame followed by `0x03` telemetry decodes the telemetry.
- Base: valid `0x04`, `0x05`, or `0xAA` frames are consumed without updating the public telemetry structure.
- Bad: accepting a checksum generated by the wrong algorithm or waiting for a 262-byte frame because the stream buffer happens to fit it.

### 6. Tests Required

- Compile `tests/jbd_bms_protocol_selftest.c` with `-Wall -Wextra -Werror`.
- Cover fixed-byte checksum vectors, fragmentation, trailing frames, non-zero status, bad CRC, bad authentication checksum, and oversized regular/authentication declarations.
- Run `./scripts/run-host-selftests.sh`; use ASan/UBSan for parser changes that affect buffer arithmetic.

### 7. Wrong vs Correct

```c
/* Wrong: the runtime buffer size is not the protocol maximum. */
if (frame_len > stream_capacity) reject_frame();

/* Correct: reject impossible protocol frames before they can stall assembly. */
if (frame_len > JBD_MAX_RESPONSE_SIZE) resynchronize();
```
